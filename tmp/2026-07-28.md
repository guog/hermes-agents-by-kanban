# Hermes completion metadata、Controller exception 与状态治理方案

## 背景

Hermes `v2026.7.20` 在 worker 为自己的 Kanban 卡调用
`kanban_complete(metadata=...)` 时，会在持久化前自动加入可信运行时字段
`worker_session_id`。Hollysys Controller 当前直接使用业务模型
`CompletionMetadata` 验证整份持久化对象；该模型采用 `extra="forbid"`，生成的
`card-completion.schema.json` 也使用 `additionalProperties=false`。因此 worker
提交的业务 metadata 即使完全有效，Controller 仍会把 Hermes 自动加入的字段当成
协议错误，确定性地耗尽同阶段重试预算。

同时，`hollysysctl` 使用未限定路径的 `python`。Dispatcher 的登录 shell 会重置
`PATH`，使其解析到不含 Controller 依赖的 `/usr/bin/python`，造成异常处理阶段无法
查询健康和状态。这个 CLI 环境错误是次生故障，不是 completion metadata 异常的原因。

恢复后又暴露出第二类协议输入：reviewer 把仅允许 authoring pass 使用的
`repository_evidence` 带入 review completion。业务模型正确拒绝了该字段，但
Pydantic `ValidationError.errors()` 的 `ctx.error` 保留了 `ValueError` 对象；
Controller 的 `_error_text` 未提供安全序列化 fallback，错误处理本身抛出
`TypeError`。轮询连续失败达到阈值后 Controller 退出，而容器中的 Dashboard 与
Gateway 仍存活，导致 Compose 显示容器运行但 Controller socket 缺失。

## 长期目标

1. 明确区分 worker 业务协议与 Hermes 可信运行时信封。
2. 保持业务 completion schema 严格，不允许 worker 伪造运行时 provenance。
3. Controller exception 可通过幂等、可审计、Controller 自有的协议恢复。
4. 系统性兼容错误修复后不永久占用业务 Agent 的协议重试预算。
5. 所有正式阶段在真实 Hermes 持久化行为下都有集成测试。
6. Profile 登录 shell、Compose exec 和 Controller daemon 使用同一受控 Python 环境。
7. 任意不可信 completion 都只能形成可审计协议失败，不能使 Controller 进程退出。
8. `checkout`、`iteration` 等 Controller 已知上下文不再依赖 Agent 手工重写。
9. 日常阶段查询不执行全量 GitLab 门禁审计，并在固定短时限内返回。
10. 慢速 GitLab 查询不持有 Controller 状态转换锁，客户端超时后不遗留后台任务。

## 1. 持久化信封模型

保留 `CompletionMetadata` 作为 worker 可写业务协议，并继续由
`card-completion.schema.json` 对其生成严格 Schema。新增独立的
`PersistedCompletionMetadata` 或等价适配器，只用于读取 Hermes 已持久化数据：

- 接受完整 `CompletionMetadata` 字段；
- 额外仅接受非空 `worker_session_id`；
- 拒绝其他未知字段；
- 将 `worker_session_id` 作为 runtime provenance 返回，不传入业务门禁判断；
- 业务字段再转换为严格 `CompletionMetadata`。

所有读取 `task.latest_metadata` 的路径必须统一经过该适配器，包括：

- 主 reconcile；
- status/gate 汇总；
- review 次数计算；
- frozen baseline 重建；
- finalization 第三次 review 证据；
- latest valid completion；
- code modification 计数。

Controller 自己生成的 completion metadata 和 Worker 输入 Schema 不经过运行时信封
放宽，避免把兼容逻辑扩散到写入侧。

## 2. provenance 校验

`worker_session_id` 不只是忽略字段。长期实现应：

- 限制为非空、合理长度的字符串；
- 在 Hermes 提供可查询 session/run 关联时，核对它与当前 task run；
- 在状态和审计记录中单独展示，不参与 GitLab gate 或 artifact digest；
- 对缺失运行时标记保持兼容，因为 Controller 自己的完成、管理员恢复和历史记录可能
  没有 worker session。

不得把 `worker_session_id` 加入 worker 可写的
`card-completion.schema.json`，否则会把可信运行时事实降级为 Agent 可伪造字段。

## 3. Controller 上下文信封

`run_key`、stage、iteration、mode、project、checkout/worktree、branch、PRD、
card ID 等值均由 Controller 发卡时确定。长期协议不应要求 Agent 重新手工生成这些
冗余字段：

- Worker 只提交 outcome、工件、门禁、仓库证据、验证、决策和风险等业务 payload。
- Hermes 完成工具或 Controller ingestion adapter 根据当前 task/card 自动加盖
  Controller context envelope。
- 在持久化前提供 `validate-completion` 入口，使用当前卡片验证完整业务 payload，
  而不是等卡片完成后才发现上下文错误。
- 严禁根据父卡、前一次 metadata、review 次数、终端 cwd 或聊天记忆推导 iteration
  与 checkout。
- `repository_evidence.inspected_paths` 仅表示 `repository_base_sha` 上存在的路径；
  本轮新增工件由 `artifact_paths` 表示。验证进程必须使用与 daemon 相同的运行用户，
  避免 Git `safe.directory`/ownership 差异造成假阴性。

## 4. Controller exception 恢复协议

新增独立 RPC/CLI：

```text
hollysysctl recover-exception \
  --run-key <run-key> \
  --card-id <exception-card-id> \
  --reason <operator-reason>
```

恢复操作必须：

1. 验证 run 为 v2，活动卡唯一且是 Controller 创建、管理的 exception 卡。
2. 验证 exception 的 parent 是最近完成的正式 work card。
3. 使用当前版本的持久化信封适配器重新验证 parent completion。
4. 重新读取 Kanban、GitLab MR/head、冻结工件、artifact digest 和身份事实。
5. 如果 head 或工件已经漂移，拒绝复用旧结果并由 Controller 创建绑定当前事实的
   repair attempt。
6. 如果 parent 重新验证通过，写入
   `[controller-exception-resolution:v1]` 审计评论，由 Controller 完成 exception 卡。
7. 幂等触发 reconcile，直接从已验证 parent 进入下一阶段，不重复创建 run、worktree、
   分支或 MR。
8. 重复调用返回同一结果，不创建重复卡。

Dispatcher 只负责把管理员批准的恢复请求传给 Controller，不直接
`kanban unblock/complete/promote/edit`。

## 5. 协议重试预算

当前重试统计只要看到 `[controller-protocol-error:v2]` 就永久计数。长期实现应引入
“协议失败 episode”或恢复标记：

- 未解决的连续协议错误才消耗当前预算；
- `controller-exception-resolution` 可将已确认的系统性兼容错误标记为 resolved；
- 原错误评论和事件永久保留，不删除历史；
- status 同时展示 historical、resolved、active 三种计数；
- 后续阶段或以后重新进入同一阶段时，不因已经修复的兼容错误立即零预算异常。

## 6. Python 运行环境

`hollysysctl` 必须固定使用受控解释器：

```sh
exec /opt/hermes/.venv/bin/python -m hollysys_controller.cli "$@"
```

可以提供显式的只读覆盖变量用于镜像升级兼容，但不得静默回退到
`/usr/bin/python`。Controller daemon、healthcheck 和 CLI 应共享同一依赖基线。

## 7. 错误隔离与进程存活

- `_error_text` 必须能安全序列化 Pydantic `ctx` 中的异常对象，输出有长度上限且不得
  包含原始敏感输入。
- 单张卡的 metadata、gate 或外部证据错误必须在 run 级收敛为协议重试或 exception，
  不得逃逸到全局 polling/reconcile loop。
- `fatal_loop_error_limit` 只用于 Controller 自身不可恢复故障；业务输入错误不得累计
  为 daemon fatal。
- 容器健康检查同时覆盖 PID 与 Unix socket；Dashboard/Gateway 存活不能掩盖
  Controller 主服务退出。
- 正式部署应让 Controller 具有独立、可监督的服务生命周期；若继续复用同一容器，
  s6 必须在 Controller 退出时重启该服务或使容器退出，从而触发 Compose
  `restart: unless-stopped`。

## 8. 状态查询与对账性能

### 2026-07-29 运行态问题

一次真实运行中，Dispatcher 连续两次调用 `hollysysctl status`，均在约 130.5 秒后
超时；同期 `health` 在 1 秒内返回正常。现场确认：

- `status()` 与 `reconcile_all()` 共用同一把全局锁；
- `status()` 持锁串行执行 MR、五类 gate、artifact 和 frozen baseline 校验；
- GitLab 适配器为单次状态查询重复执行
  `repository/tree?recursive=true` 全仓扫描和逐工件 file/blob 请求；
- 现场一个递归 tree 子进程持续数十秒，外部命令超时上限为 120 秒；
- RPC 客户端超时为 130 秒，`asyncio.to_thread()` 中的服务端工作不会随客户端取消；
- 服务端最终向已断开的 socket 回写，产生 `ConnectionResetError` 和
  `BrokenPipeError`；
- event cursor 与 `last_reconcile_at` 仍持续前进，证明是查询延迟和锁竞争，不是
  Controller 离线或 Run 状态损坏。

### 查询分层

拆分日常状态与完整审计：

1. `status-summary` 只读取 Controller store、Kanban 快照、活动卡、事件游标、
   `last_reconcile_at/error` 和最近已缓存的 MR/head；不得执行外部 GitLab I/O，
   目标 2 秒内返回。
2. `status-audit` 执行完整 GitLab/gate/frozen artifact 复核，作为异步、可观察、
   可取消的审计任务；返回 audit id、开始时间、当前步骤和最后成功快照。
3. 普通 Dispatcher 状态答复使用 summary，并明确 `live_audit_at` 与是否过期；
   只有管理员或合并门禁需要时才触发 audit。
4. merge/reconcile 仍以当前 GitLab 事实为准，不得用 summary 缓存替代 checked-head
   门禁。

### 锁与一致性

- 全局 mutation lock 只保护卡片创建、完成、恢复、cursor/operation/outbox 更新等
  状态转换。
- 查询在锁内取得带版本号的本地一致快照后立即释放锁；外部 GitLab I/O 在锁外执行。
- 外部校验结束后，发布结果或执行状态转换前重新核对 run version、event cursor 和
  MR head；漂移则丢弃旧结果并重算。
- 同一 `run + head + audit-kind` 使用 single-flight，重复查询复用一个在途任务，
  不创建排队线程。

### GitLab 请求治理

- 一次 audit 内 MR 只读取一次，同一 ref 的 tree/blob/gate note 结果只计算一次。
- 禁止为已知工件路径反复递归扫描整个仓库。优先按工件根目录查询，或对 completion
  中的精确路径读取 blob；需要证明“没有额外工件”时只扫描配置的工件目录。
- 可以在确认本地 worktree HEAD/upstream 等于当前 GitLab MR head 后，使用本地 Git
  对象批量计算 path/blob digest；GitLab 仍负责提供 checked head 和评论身份事实。
- 记录每个 GitLab endpoint 的调用次数、耗时、超时和 cache hit，避免 status
  随冻结阶段数量线性重复增长。

### Deadline、取消与可观测性

- summary 使用独立短 deadline；audit 使用总 deadline 和逐步骤 deadline，不允许
  每个子命令分别消耗完整 120 秒后继续下一步。
- 客户端断开或 deadline 到达时，取消剩余 audit 并终止其子进程；不得只取消
  `await` 而让 `to_thread` 继续运行。
- RPC 写回前检查 transport 状态；对客户端已断开只记录结构化取消事件，不产生
  未处理的 BrokenPipe traceback。
- health 增加 `mutation_lock_wait_seconds`、`status_inflight`、`audit_inflight`、
  当前 endpoint/elapsed、`last_audit_at/error/head` 和 reconcile age。

### 当前版本临时处置

在上述改造部署前：

1. 若 `event_cursor` 和 `last_reconcile_at` 持续前进、无 reconcile error，则不要
   重启 Controller；这属于慢查询，不是死锁。
2. `status` 超时后不得立即重复调用。重复调用会留下仍在执行或等待全局锁的服务端
   thread，并进一步延迟 reconcile。
3. Dispatcher 先报告 `health` 与“完整状态审计繁忙”，管理员用只读 Kanban/SQLite
   快照诊断活动卡；不得把该快照冒充完整 GitLab 门禁结论。
4. 只有外部命令超过 120 秒仍未退出，并且 `last_reconcile_at` 超过
   `command_timeout + 2 * reconcile_interval` 不再前进时，才在保存在线 SQLite
   备份后重启 Controller。
5. 当前活动 worker 运行时不为部署 summary 热修复而重启容器；等待卡片到达安全边界
   后再部署，避免杀死正在执行的 Agent。
6. `status-summary` 的本地只读进程不得复用 Dispatcher/worker 的 profile
   `HERMES_HOME`；应从 Controller `state_dir` 或独立的
   `HOLLYSYS_CONTROLLER_HERMES_HOME` 得到 `/opt/data`，并以实际 profile terminal
   环境做验收。
7. 为恢复已经完成但多带 authoring-only `repository_evidence` 的 reviewer 卡，允许
   persisted adapter 临时丢弃该字段；公开 schema 仍严格拒绝，gate/head/digest
   仍由 Controller 独立验证。所有 reviewer/tester Skill 修正并连续运行无此类
   metadata 后删除该兼容分支，恢复“发现即协议失败”的长期契约。
8. 协议预算耗尽后的恢复必须先修复并验证解析边界，再完成既有 exception 卡，让
   Controller 重新验证最后一张已完成工作卡；不得伪造 reviewer 结果或跳过 gate。

## 9. 测试要求

### 单元测试

- Worker `CompletionMetadata` 继续拒绝 `worker_session_id`。
- Persisted adapter 接受合法 `worker_session_id`。
- Persisted adapter 拒绝其他 extra 字段和非法 session id。
- 所有 stored completion 读取路径使用统一适配器。
- exception recovery 校验错误 run/card/parent/head/digest 时 fail closed。
- recovery 幂等且不重复创建下一卡。
- resolved 协议 episode 不再占用 active retry budget。
- 带 `repository_evidence` 的 reviewer completion 被记为协议失败并重派 reviewer。
- Pydantic model-validator 的 `ctx.error` 可序列化，轮询和 socket 保持存活。
- Reviewer Skill 明确区分“必须核实仓库证据”和“不得提交 authoring-only
  `repository_evidence` 字段”，并覆盖 SPEC/PLAN/TASKS/CODE review。
- 所有 authoring Skill 在完成前从当前卡片复制上下文，并验证 evidence path 存在于
  `repository_base_sha`。
- 旧 checkout 或 review iteration 的 metadata 在持久化前被拒绝，卡片保持可重试。
- summary 在 GitLab 延迟、失败或全局 audit 正在运行时仍能在 2 秒内返回。
- 两个相同 status/audit 请求只产生一个 GitLab 调用序列。
- RPC 客户端超时会取消服务端任务和子进程，不遗留线程或 BrokenPipe traceback。
- 慢 audit 不阻塞 Kanban event polling、reconcile 状态转换和 health。
- 单次 audit 对同一 MR/head 的递归 tree 查询不超过一次，精确工件目录优先。

### 集成测试

- 模拟 Hermes `kanban_complete` 在持久化前自动加入 `worker_session_id`。
- 覆盖 SPEC、PLAN、TASKS、IMPLEMENT、TEST、CODE-REVIEW。
- 验证同一 head 的 tester/code-reviewer 双门禁不受运行时字段影响。
- 从真实 Controller exception 执行 recover，确认进入精确下一阶段。
- 在精简 `PATH=/usr/local/bin:/usr/bin:/bin` 下运行
  `hollysysctl health/status`。
- 对大型仓库注入 30/120 秒 GitLab tree 延迟，验证 summary deadline、audit
  single-flight、取消传播和锁外 I/O。

### 运行态验收

- Controller、Kanban、GitLab health 均正常。
- 无 pending outbox、failed operation 和 reconcile error。
- 恢复后不会创建重复 worktree、branch、MR 或业务卡。
- status 中 exception 已解决，活动卡是预期下一阶段。
- 后续至少完成一个带 Hermes runtime stamp 的真实阶段交接。
- status-summary p95 小于 2 秒，status-audit 有明确进度且不阻塞 reconcile。

## 10. 部署与回滚

- 不修改官方镜像内 `/opt/hermes`。
- 通过本仓库挂载的 Controller、wrapper 和测试交付修复。
- 部署继续使用选定镜像 tag；目标机已有镜像时使用 `--pull never`。
- 变更前使用 SQLite online backup 保存 Controller store 和对应 board DB。
- 回滚时恢复代码版本；只有在恢复操作已经改变流程状态且业务要求回退时，才使用受控
  数据恢复。不得直接复制活动 WAL 文件。

## 完成标准

长期方案完成需要同时满足：

1. 运行时信封与业务 Schema 明确分层。
2. 正式 exception recovery RPC 可用且幂等。
3. 已解决的基础设施协议错误不再占用活动预算。
4. Dispatcher 在真实登录 shell 中可稳定调用 `hollysysctl`。
5. 真实 Hermes runtime-stamp E2E 通过。
6. 文档、模型、生成 Schema、Controller 行为和部署验证保持一致。
7. 非法 reviewer metadata 的真实运行态测试不会终止 Controller。
8. 日常状态查询与完整 GitLab 审计分层，慢审计不会阻塞控制循环。

## 12. 临时防护的覆盖范围与剩余技术债

### 已覆盖的已知输入

`hollysys_controller/models.py:431-460` 的临时 persisted adapter：

- 接受并剥离 Hermes 运行时加入的非空 `worker_session_id`；
- 仅对 SPEC/PLAN/TASKS review、TEST、CODE REVIEW 剥离无授权意义的
  `repository_evidence`；
- 公开 worker schema 仍保持严格；
- 其他 extra 和全部业务字段仍由 `CompletionMetadata` 严格验证。

TASKS 和 CODE authoring Skill 已明确要求在完成前重读当前卡片：

- `checkout` 必须取 `run.workspace.checkout`；
- `iteration` 必须取当前卡，而不是 review 次数、父卡或历史 metadata；
- `repository_evidence.inspected_paths` 必须在 `repository_base_sha` 上真实存在；
- 本轮新产物只能放入 `artifact_paths`。

TASKS reviewer、tester 和 code-reviewer Skill 已明确禁止提交
authoring-only `repository_evidence`。tester 与 code-reviewer 都必须在发布结论前
重读 MR head，并把 gate 绑定到同一精确 head。

`hollysys_controller/cli.py:18-22,81-93` 使 `status-summary` 从 Controller
`state_dir` 推导真实数据根，不再复用 Dispatcher profile 的 `HERMES_HOME`；
`status-summary` 直接读取本地只读快照，不经过会执行 GitLab 完整审计的 RPC。

### 临时防护没有解决的部分

1. Adapter 只兼容已经确认的两个非权威 extra，不会自动修正
   `run_key/checkout/iteration/stage/card`。所以 Agent 仍可能产生新的上下文错误。
2. Profile Skill 是行为约束，不是类型系统。它降低 Agent 填错概率，但不能替代
   Controller context envelope 和完成前校验。
3. 临时丢弃 reviewer `repository_evidence` 会掩盖 Agent 尚未完全遵守协议的事实。
   必须增加 telemetry，并在连续真实 E2E 无此输入后删除兼容分支。
4. `status-summary` 解决了 Dispatcher 的日常查询路径，但完整 `status` 的全量
   GitLab 扫描、锁竞争、取消传播和 BrokenPipe 问题仍未根治。
5. 当前 120 秒 `command_timeout_seconds` 约束 GitLab、Kanban、通知等外部命令，
   没有形成每个 stage worker 的 wall-clock watchdog。
6. Controller 虽然实现两次协议重试和五次代码修改上限，但“worker 进程存活却长期
   不完成”不是协议失败，不会自然消耗这些预算。

## 13. TASKS 之后的逐阶段停滞风险

| 阶段 | 已有控制 | 仍可能停滞的原因 | 当前风险 |
| --- | --- | --- | --- |
| TASKS-WRITE | 当前卡上下文复制、严格 repository evidence | Agent 漏字段或仍复制错误 context；worker 长时间不完成 | 低到中 |
| TASKS-REVIEW | review gate、禁止 reviewer repository evidence、临时 adapter | 其他必填字段缺失；gate 身份、digest 或 artifact head 不一致 | 低到中 |
| IMPLEMENT | 精确 worktree/branch/MR、冻结基线、最多五轮修改、完成后 MR Ready | 实现耗时无 stage deadline；流水线或外部依赖长时间运行 | 中 |
| TEST | 当前 MR head、结构化 `skipped_unavailable`、不得修改代码 | 测试环境不可用、head 漂移、completion 上下文错误 | 中但可观测 |
| CODE-REVIEW | 与 tester 同 head、独立 GitLab 身份、汇总两方 findings | head 漂移会回到 TEST；失败最多进入五轮修复 | 中但受控 |
| MERGE | checked-head merge、pipeline、讨论、可合并性检查 | 条件不满足时无活动卡、只每 30 秒重试，缺少显式等待状态和通知 | 高 |

### 最终合并是现版本最明显的“看起来不动”路径

`hollysys_controller/gitlab.py:722-777` 要求：

- MR 已不是 Draft；
- tester 与 code-reviewer 都绑定当前 MR/head；
- 两个 gate 来自独立 GitLab 用户；
- MR 状态为 mergeable；
- 当前 head 的 required pipeline 必须为 `success`；
- 不存在未解决的 blocking discussion。

这些门禁本身是正确的。但 `hollysys_controller/service.py:1147-1158` 在
pipeline、discussion 或 MR readiness 不满足时，只返回并等待 30 秒后的 reconcile：

- 不创建活动卡；
- 不进入 exception；
- 不写出明确 `merge-wait` 状态；
- 不发送带 blocker 的通知；
- 没有等待总时限。

因此“TEST 和 CODE REVIEW 都完成、Controller health 正常、但没有活动卡也没有
合并”可能持续存在。这不是死锁，却会在用户侧表现为流程卡住，是长期改造的最高优先级
可观测性缺口。

### CODE 双门禁属于受控停止

`hollysys_controller/workflow.py:86-113` 的行为是：

1. TEST 完成后总是进入独立 CODE REVIEW，不因 test fail 提前跳过 review。
2. TEST 与 CODE REVIEW 不是同一 MR/head 时，重新从 TEST 开始。
3. 两者都 pass 且绑定同一 delivery 时才允许 merge。
4. 任一失败则回到 IMPLEMENT，最多五次 code modification。
5. 五次后仍未同时通过，形成明确 blocked/exception，由人类决定。

这一段可能停止自动流程，但属于有预算、有原因、有人工动作的受控停止，不应与无状态的
merge wait 或 worker hang 混为一类。

## 14. 长期改造新增要求

### Stage worker lease 与 watchdog

为每张正式工作卡持久化：

- `worker_started_at`
- `worker_session_id`
- `last_heartbeat_at`
- `last_progress_event_at`
- `deadline_at`
- `worker_pid/session_status` 的最近可信快照

Controller 必须区分：

1. 正常长任务：heartbeat 和 progress 持续；
2. worker 已退出：无进程/无 session，但卡仍 running；
3. worker 假活：有 heartbeat，但超过 stage progress deadline 无业务进展；
4. 外部依赖等待：有明确 dependency、deadline 和最近检查结果。

超时后先采集卡片、session、进程、最后事件和 worktree 证据，再进行有限重派；达到预算
后创建 exception。不得无限等待，也不得仅凭总运行时长杀死仍有真实进展的任务。

### 显式 merge-wait 状态

把当前 cardless retry 改为可持久化状态，例如：

```text
phase=code
stage=merge-wait
blocker=draft|pipeline_pending|pipeline_failed|not_mergeable|unresolved_discussion
mr_iid=<iid>
head_sha=<sha>
first_seen_at=<time>
last_checked_at=<time>
next_retry_at=<time>
```

要求：

- pipeline pending 时正常等待并显示 pipeline URL；
- pipeline failed/skipped 时立即形成可操作通知，不无限重试；
- Draft MR 超过短宽限期后通知 coder/管理员；
- unresolved discussion 列出 discussion URL 和责任人；
- blocker 变化产生事件，但相同 blocker 的轮询保持幂等；
- 超过可配置总时限后创建 merge exception，不消耗 Agent 协议预算；
- 合并前仍重新执行 checked-head 校验，不能因为等待状态而放宽门禁。

### Controller context envelope

长期移除 Agent 对以下字段的自由填写权：

- run、stage、iteration、mode；
- board、project、checkout、branch；
- card ID、parent ID；
- MR identity 中 Controller 已知且不可变的部分。

完成工具只接收业务 payload，Hermes/Controller 根据当前 scoped card 加盖 context。
若短期仍保留当前 schema，至少增加：

```text
hollysysctl validate-completion --card-id <id> --metadata <file>
```

它必须在 `kanban_complete` 前验证当前卡片上下文、schema、路径、MR/head 和字段权限，
避免“卡已经完成后才由 reconcile 发现错误”。

### 状态与通知验收

后续 E2E 必须分别制造并验证：

- worker 正常长任务；
- worker 退出但卡仍 running；
- completion 漏 `run_key`；
- 错 `checkout/iteration`；
- Hermes 注入 `worker_session_id`；
- reviewer 多带 `repository_evidence`；
- GitLab tree 查询超过 120 秒；
- MR 保持 Draft；
- pipeline pending、failed、skipped、success；
- unresolved discussion；
- TEST/CODE REVIEW head 漂移；
- 五次代码修复耗尽。

每一种情况都要断言：

- Controller daemon/socket 是否存活；
- `status-summary` 是否在 2 秒内返回；
- active card 或显式 wait/exception 是否唯一；
- event cursor 是否推进；
- outbox 通知是否幂等；
- 是否给出准确的人类动作；
- 重启后能否从持久化状态继续；
- 是否保持同一 run/worktree/branch/MR/head provenance。

## 15. 运维判定规则

### 不应立即重启

- `health=ok`；
- `event_lag=0` 或没有持续增加；
- active card 对应 worker 存在且有 heartbeat/progress；
- 只是完整 `status` 超时，而 `status-summary` 可快速返回；
- 正在执行已知 GitLab audit，且 endpoint/elapsed 仍变化。

### 必须进一步诊断

- active card 长时间不变且对应 worker/session 已消失；
- heartbeat 存在但超过 stage progress deadline 无业务事件；
- `event_lag` 持续增长；
- `last_reconcile_at` 超过
  `command_timeout + 2 * reconcile_interval` 不再前进；
- TEST/CODE REVIEW 完成后无 active card，且 merge blocker 未公开；
- socket 缺失、daemon 不存在或 `last_reconcile_error` 连续出现。

### 重启前必须保全

- `status-summary` 与 `health` 原始输出；
- Controller PID、worker PID/session、运行时长和命令；
- Controller 最近日志与当前 GitLab 子进程；
- Controller store 和对应 Kanban DB 的 SQLite online backup；
- 当前 run/card/iteration/worktree/branch/MR/head；
- pending outbox、failed operations 和 event cursor。

重启只恢复服务生命周期，不能解决非法 completion、错误 context、pipeline failure、
unresolved discussion 或 worker 业务逻辑停滞。恢复后必须核对 socket、cursor 和
唯一活动卡，不得重复创建 worktree、branch、MR 或下一阶段卡。
