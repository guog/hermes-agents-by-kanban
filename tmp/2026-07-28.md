# Hermes completion metadata、Controller exception 与状态治理方案

## 背景

Hermes `v2026.7.20` 在 worker 为自己的 Kanban 卡调用
`kanban_complete(metadata=...)` 时，会在持久化前自动加入可信运行时字段
`worker_session_id`。Hollysys Controller 当前直接使用业务模型
`CompletionMetadata` 验证整份持久化对象；该模型采用 `extra="forbid"`，生成的
`card-completion.schema.json` 也使用 `additionalProperties=false`。因此 worker
提交的业务 metadata 即使完全有效，Controller 仍会把 Hermes 自动加入的字段当成
协议错误，确定性地耗尽同阶段重试预算。

同时，`hollysysctl` 使用未限定路径的 `python`。Dispatcher 的登录 shell 会重置
`PATH`，使其解析到不含 Controller 依赖的 `/usr/bin/python`，造成异常处理阶段无法
查询健康和状态。这个 CLI 环境错误是次生故障，不是 completion metadata 异常的原因。

恢复后又暴露出第二类协议输入：reviewer 把仅允许 authoring pass 使用的
`repository_evidence` 带入 review completion。业务模型正确拒绝了该字段，但
Pydantic `ValidationError.errors()` 的 `ctx.error` 保留了 `ValueError` 对象；
Controller 的 `_error_text` 未提供安全序列化 fallback，错误处理本身抛出
`TypeError`。轮询连续失败达到阈值后 Controller 退出，而容器中的 Dashboard 与
Gateway 仍存活，导致 Compose 显示容器运行但 Controller socket 缺失。

## 长期目标

1. 明确区分 worker 业务协议与 Hermes 可信运行时信封。
2. 保持业务 completion schema 严格，不允许 worker 伪造运行时 provenance。
3. Controller exception 可通过幂等、可审计、Controller 自有的协议恢复。
4. 系统性兼容错误修复后不永久占用业务 Agent 的协议重试预算。
5. 所有正式阶段在真实 Hermes 持久化行为下都有集成测试。
6. Profile 登录 shell、Compose exec 和 Controller daemon 使用同一受控 Python 环境。
7. 任意不可信 completion 都只能形成可审计协议失败，不能使 Controller 进程退出。
8. `checkout`、`iteration` 等 Controller 已知上下文不再依赖 Agent 手工重写。
9. 日常阶段查询不执行全量 GitLab 门禁审计，并在固定短时限内返回。
10. 慢速 GitLab 查询不持有 Controller 状态转换锁，客户端超时后不遗留后台任务。

## 1. 持久化信封模型

保留 `CompletionMetadata` 作为 worker 可写业务协议，并继续由
`card-completion.schema.json` 对其生成严格 Schema。新增独立的
`PersistedCompletionMetadata` 或等价适配器，只用于读取 Hermes 已持久化数据：

- 接受完整 `CompletionMetadata` 字段；
- 额外仅接受非空 `worker_session_id`；
- 拒绝其他未知字段；
- 将 `worker_session_id` 作为 runtime provenance 返回，不传入业务门禁判断；
- 业务字段再转换为严格 `CompletionMetadata`。

所有读取 `task.latest_metadata` 的路径必须统一经过该适配器，包括：

- 主 reconcile；
- status/gate 汇总；
- review 次数计算；
- frozen baseline 重建；
- finalization 第三次 review 证据；
- latest valid completion；
- code modification 计数。

Controller 自己生成的 completion metadata 和 Worker 输入 Schema 不经过运行时信封
放宽，避免把兼容逻辑扩散到写入侧。

## 2. provenance 校验

`worker_session_id` 不只是忽略字段。长期实现应：

- 限制为非空、合理长度的字符串；
- 在 Hermes 提供可查询 session/run 关联时，核对它与当前 task run；
- 在状态和审计记录中单独展示，不参与 GitLab gate 或 artifact digest；
- 对缺失运行时标记保持兼容，因为 Controller 自己的完成、管理员恢复和历史记录可能
  没有 worker session。

不得把 `worker_session_id` 加入 worker 可写的
`card-completion.schema.json`，否则会把可信运行时事实降级为 Agent 可伪造字段。

## 3. Controller 上下文信封

`run_key`、stage、iteration、mode、project、checkout/worktree、branch、PRD、
card ID 等值均由 Controller 发卡时确定。长期协议不应要求 Agent 重新手工生成这些
冗余字段：

- Worker 只提交 outcome、工件、门禁、仓库证据、验证、决策和风险等业务 payload。
- Hermes 完成工具或 Controller ingestion adapter 根据当前 task/card 自动加盖
  Controller context envelope。
- 在持久化前提供 `validate-completion` 入口，使用当前卡片验证完整业务 payload，
  而不是等卡片完成后才发现上下文错误。
- 严禁根据父卡、前一次 metadata、review 次数、终端 cwd 或聊天记忆推导 iteration
  与 checkout。
- `repository_evidence.inspected_paths` 仅表示 `repository_base_sha` 上存在的路径；
  本轮新增工件由 `artifact_paths` 表示。验证进程必须使用与 daemon 相同的运行用户，
  避免 Git `safe.directory`/ownership 差异造成假阴性。

## 4. Controller exception 恢复协议

新增独立 RPC/CLI：

```text
hollysysctl recover-exception \
  --run-key <run-key> \
  --card-id <exception-card-id> \
  --reason <operator-reason>
```

恢复操作必须：

1. 验证 run 为 v2，活动卡唯一且是 Controller 创建、管理的 exception 卡。
2. 验证 exception 的 parent 是最近完成的正式 work card。
3. 使用当前版本的持久化信封适配器重新验证 parent completion。
4. 重新读取 Kanban、GitLab MR/head、冻结工件、artifact digest 和身份事实。
5. 如果 head 或工件已经漂移，拒绝复用旧结果并由 Controller 创建绑定当前事实的
   repair attempt。
6. 如果 parent 重新验证通过，写入
   `[controller-exception-resolution:v1]` 审计评论，由 Controller 完成 exception 卡。
7. 幂等触发 reconcile，直接从已验证 parent 进入下一阶段，不重复创建 run、worktree、
   分支或 MR。
8. 重复调用返回同一结果，不创建重复卡。

Dispatcher 只负责把管理员批准的恢复请求传给 Controller，不直接
`kanban unblock/complete/promote/edit`。

## 5. 协议重试预算

当前重试统计只要看到 `[controller-protocol-error:v2]` 就永久计数。长期实现应引入
“协议失败 episode”或恢复标记：

- 未解决的连续协议错误才消耗当前预算；
- `controller-exception-resolution` 可将已确认的系统性兼容错误标记为 resolved；
- 原错误评论和事件永久保留，不删除历史；
- status 同时展示 historical、resolved、active 三种计数；
- 后续阶段或以后重新进入同一阶段时，不因已经修复的兼容错误立即零预算异常。

## 6. Python 运行环境

`hollysysctl` 必须固定使用受控解释器：

```sh
exec /opt/hermes/.venv/bin/python -m hollysys_controller.cli "$@"
```

可以提供显式的只读覆盖变量用于镜像升级兼容，但不得静默回退到
`/usr/bin/python`。Controller daemon、healthcheck 和 CLI 应共享同一依赖基线。

## 7. 错误隔离与进程存活

- `_error_text` 必须能安全序列化 Pydantic `ctx` 中的异常对象，输出有长度上限且不得
  包含原始敏感输入。
- 单张卡的 metadata、gate 或外部证据错误必须在 run 级收敛为协议重试或 exception，
  不得逃逸到全局 polling/reconcile loop。
- `fatal_loop_error_limit` 只用于 Controller 自身不可恢复故障；业务输入错误不得累计
  为 daemon fatal。
- 容器健康检查同时覆盖 PID 与 Unix socket；Dashboard/Gateway 存活不能掩盖
  Controller 主服务退出。
- 正式部署应让 Controller 具有独立、可监督的服务生命周期；若继续复用同一容器，
  s6 必须在 Controller 退出时重启该服务或使容器退出，从而触发 Compose
  `restart: unless-stopped`。

## 8. 状态查询与对账性能

### 2026-07-29 运行态问题

一次真实运行中，Dispatcher 连续两次调用 `hollysysctl status`，均在约 130.5 秒后
超时；同期 `health` 在 1 秒内返回正常。现场确认：

- `status()` 与 `reconcile_all()` 共用同一把全局锁；
- `status()` 持锁串行执行 MR、五类 gate、artifact 和 frozen baseline 校验；
- GitLab 适配器为单次状态查询重复执行
  `repository/tree?recursive=true` 全仓扫描和逐工件 file/blob 请求；
- 现场一个递归 tree 子进程持续数十秒，外部命令超时上限为 120 秒；
- RPC 客户端超时为 130 秒，`asyncio.to_thread()` 中的服务端工作不会随客户端取消；
- 服务端最终向已断开的 socket 回写，产生 `ConnectionResetError` 和
  `BrokenPipeError`；
- event cursor 与 `last_reconcile_at` 仍持续前进，证明是查询延迟和锁竞争，不是
  Controller 离线或 Run 状态损坏。

### 查询分层

拆分日常状态与完整审计：

1. `status-summary` 只读取 Controller store、Kanban 快照、活动卡、事件游标、
   `last_reconcile_at/error` 和最近已缓存的 MR/head；不得执行外部 GitLab I/O，
   目标 2 秒内返回。
2. `status-audit` 执行完整 GitLab/gate/frozen artifact 复核，作为异步、可观察、
   可取消的审计任务；返回 audit id、开始时间、当前步骤和最后成功快照。
3. 普通 Dispatcher 状态答复使用 summary，并明确 `live_audit_at` 与是否过期；
   只有管理员或合并门禁需要时才触发 audit。
4. merge/reconcile 仍以当前 GitLab 事实为准，不得用 summary 缓存替代 checked-head
   门禁。

### 锁与一致性

- 全局 mutation lock 只保护卡片创建、完成、恢复、cursor/operation/outbox 更新等
  状态转换。
- 查询在锁内取得带版本号的本地一致快照后立即释放锁；外部 GitLab I/O 在锁外执行。
- 外部校验结束后，发布结果或执行状态转换前重新核对 run version、event cursor 和
  MR head；漂移则丢弃旧结果并重算。
- 同一 `run + head + audit-kind` 使用 single-flight，重复查询复用一个在途任务，
  不创建排队线程。

### GitLab 请求治理

- 一次 audit 内 MR 只读取一次，同一 ref 的 tree/blob/gate note 结果只计算一次。
- 禁止为已知工件路径反复递归扫描整个仓库。优先按工件根目录查询，或对 completion
  中的精确路径读取 blob；需要证明“没有额外工件”时只扫描配置的工件目录。
- 可以在确认本地 worktree HEAD/upstream 等于当前 GitLab MR head 后，使用本地 Git
  对象批量计算 path/blob digest；GitLab 仍负责提供 checked head 和评论身份事实。
- 记录每个 GitLab endpoint 的调用次数、耗时、超时和 cache hit，避免 status
  随冻结阶段数量线性重复增长。

### Deadline、取消与可观测性

- summary 使用独立短 deadline；audit 使用总 deadline 和逐步骤 deadline，不允许
  每个子命令分别消耗完整 120 秒后继续下一步。
- 客户端断开或 deadline 到达时，取消剩余 audit 并终止其子进程；不得只取消
  `await` 而让 `to_thread` 继续运行。
- RPC 写回前检查 transport 状态；对客户端已断开只记录结构化取消事件，不产生
  未处理的 BrokenPipe traceback。
- health 增加 `mutation_lock_wait_seconds`、`status_inflight`、`audit_inflight`、
  当前 endpoint/elapsed、`last_audit_at/error/head` 和 reconcile age。

### 当前版本临时处置

在上述改造部署前：

1. 若 `event_cursor` 和 `last_reconcile_at` 持续前进、无 reconcile error，则不要
   重启 Controller；这属于慢查询，不是死锁。
2. `status` 超时后不得立即重复调用。重复调用会留下仍在执行或等待全局锁的服务端
   thread，并进一步延迟 reconcile。
3. Dispatcher 先报告 `health` 与“完整状态审计繁忙”，管理员用只读 Kanban/SQLite
   快照诊断活动卡；不得把该快照冒充完整 GitLab 门禁结论。
4. 只有外部命令超过 120 秒仍未退出，并且 `last_reconcile_at` 超过
   `command_timeout + 2 * reconcile_interval` 不再前进时，才在保存在线 SQLite
   备份后重启 Controller。
5. 当前活动 worker 运行时不为部署 summary 热修复而重启容器；等待卡片到达安全边界
   后再部署，避免杀死正在执行的 Agent。
6. `status-summary` 的本地只读进程不得复用 Dispatcher/worker 的 profile
   `HERMES_HOME`；应从 Controller `state_dir` 或独立的
   `HOLLYSYS_CONTROLLER_HERMES_HOME` 得到 `/opt/data`，并以实际 profile terminal
   环境做验收。
7. 为恢复已经完成但多带 authoring-only `repository_evidence` 的 reviewer 卡，允许
   persisted adapter 临时丢弃该字段；公开 schema 仍严格拒绝，gate/head/digest
   仍由 Controller 独立验证。所有 reviewer/tester Skill 修正并连续运行无此类
   metadata 后删除该兼容分支，恢复“发现即协议失败”的长期契约。
8. 协议预算耗尽后的恢复必须先修复并验证解析边界，再完成既有 exception 卡，让
   Controller 重新验证最后一张已完成工作卡；不得伪造 reviewer 结果或跳过 gate。

## 9. 测试要求

### 单元测试

- Worker `CompletionMetadata` 继续拒绝 `worker_session_id`。
- Persisted adapter 接受合法 `worker_session_id`。
- Persisted adapter 拒绝其他 extra 字段和非法 session id。
- 所有 stored completion 读取路径使用统一适配器。
- exception recovery 校验错误 run/card/parent/head/digest 时 fail closed。
- recovery 幂等且不重复创建下一卡。
- resolved 协议 episode 不再占用 active retry budget。
- 带 `repository_evidence` 的 reviewer completion 被记为协议失败并重派 reviewer。
- Pydantic model-validator 的 `ctx.error` 可序列化，轮询和 socket 保持存活。
- Reviewer Skill 明确区分“必须核实仓库证据”和“不得提交 authoring-only
  `repository_evidence` 字段”，并覆盖 SPEC/PLAN/TASKS/CODE review。
- 所有 authoring Skill 在完成前从当前卡片复制上下文，并验证 evidence path 存在于
  `repository_base_sha`。
- 旧 checkout 或 review iteration 的 metadata 在持久化前被拒绝，卡片保持可重试。
- summary 在 GitLab 延迟、失败或全局 audit 正在运行时仍能在 2 秒内返回。
- 两个相同 status/audit 请求只产生一个 GitLab 调用序列。
- RPC 客户端超时会取消服务端任务和子进程，不遗留线程或 BrokenPipe traceback。
- 慢 audit 不阻塞 Kanban event polling、reconcile 状态转换和 health。
- 单次 audit 对同一 MR/head 的递归 tree 查询不超过一次，精确工件目录优先。

### 集成测试

- 模拟 Hermes `kanban_complete` 在持久化前自动加入 `worker_session_id`。
- 覆盖 SPEC、PLAN、TASKS、IMPLEMENT、TEST、CODE-REVIEW。
- 验证同一 head 的 tester/code-reviewer 双门禁不受运行时字段影响。
- 从真实 Controller exception 执行 recover，确认进入精确下一阶段。
- 在精简 `PATH=/usr/local/bin:/usr/bin:/bin` 下运行
  `hollysysctl health/status`。
- 对大型仓库注入 30/120 秒 GitLab tree 延迟，验证 summary deadline、audit
  single-flight、取消传播和锁外 I/O。

### 运行态验收

- Controller、Kanban、GitLab health 均正常。
- 无 pending outbox、failed operation 和 reconcile error。
- 恢复后不会创建重复 worktree、branch、MR 或业务卡。
- status 中 exception 已解决，活动卡是预期下一阶段。
- 后续至少完成一个带 Hermes runtime stamp 的真实阶段交接。
- status-summary p95 小于 2 秒，status-audit 有明确进度且不阻塞 reconcile。

## 10. 部署与回滚

- 不修改官方镜像内 `/opt/hermes`。
- 通过本仓库挂载的 Controller、wrapper 和测试交付修复。
- 部署继续使用选定镜像 tag；目标机已有镜像时使用 `--pull never`。
- 变更前使用 SQLite online backup 保存 Controller store 和对应 board DB。
- 回滚时恢复代码版本；只有在恢复操作已经改变流程状态且业务要求回退时，才使用受控
  数据恢复。不得直接复制活动 WAL 文件。

## 完成标准

长期方案完成需要同时满足：

1. 运行时信封与业务 Schema 明确分层。
2. 正式 exception recovery RPC 可用且幂等。
3. 已解决的基础设施协议错误不再占用活动预算。
4. Dispatcher 在真实登录 shell 中可稳定调用 `hollysysctl`。
5. 真实 Hermes runtime-stamp E2E 通过。
6. 文档、模型、生成 Schema、Controller 行为和部署验证保持一致。
7. 非法 reviewer metadata 的真实运行态测试不会终止 Controller。
8. 日常状态查询与完整 GitLab 审计分层，慢审计不会阻塞控制循环。

## 12. 临时防护的覆盖范围与剩余技术债

### 已覆盖的已知输入

`hollysys_controller/models.py:431-460` 的临时 persisted adapter：

- 接受并剥离 Hermes 运行时加入的非空 `worker_session_id`；
- 仅对 SPEC/PLAN/TASKS review、TEST、CODE REVIEW 剥离无授权意义的
  `repository_evidence`；
- 公开 worker schema 仍保持严格；
- 其他 extra 和全部业务字段仍由 `CompletionMetadata` 严格验证。

TASKS 和 CODE authoring Skill 已明确要求在完成前重读当前卡片：

- `checkout` 必须取 `run.workspace.checkout`；
- `iteration` 必须取当前卡，而不是 review 次数、父卡或历史 metadata；
- `repository_evidence.inspected_paths` 必须在 `repository_base_sha` 上真实存在；
- 本轮新产物只能放入 `artifact_paths`。

TASKS reviewer、tester 和 code-reviewer Skill 已明确禁止提交
authoring-only `repository_evidence`。tester 与 code-reviewer 都必须在发布结论前
重读 MR head，并把 gate 绑定到同一精确 head。

`hollysys_controller/cli.py:18-22,81-93` 使 `status-summary` 从 Controller
`state_dir` 推导真实数据根，不再复用 Dispatcher profile 的 `HERMES_HOME`；
`status-summary` 直接读取本地只读快照，不经过会执行 GitLab 完整审计的 RPC。

### 临时防护没有解决的部分

1. Adapter 只兼容已经确认的两个非权威 extra，不会自动修正
   `run_key/checkout/iteration/stage/card`。所以 Agent 仍可能产生新的上下文错误。
2. Profile Skill 是行为约束，不是类型系统。它降低 Agent 填错概率，但不能替代
   Controller context envelope 和完成前校验。
3. 临时丢弃 reviewer `repository_evidence` 会掩盖 Agent 尚未完全遵守协议的事实。
   必须增加 telemetry，并在连续真实 E2E 无此输入后删除兼容分支。
4. `status-summary` 解决了 Dispatcher 的日常查询路径，但完整 `status` 的全量
   GitLab 扫描、锁竞争、取消传播和 BrokenPipe 问题仍未根治。
5. 当前 120 秒 `command_timeout_seconds` 约束 GitLab、Kanban、通知等外部命令，
   没有形成每个 stage worker 的 wall-clock watchdog。
6. Controller 虽然实现两次协议重试和五次代码修改上限，但“worker 进程存活却长期
   不完成”不是协议失败，不会自然消耗这些预算。

## 13. TASKS 之后的逐阶段停滞风险

| 阶段 | 已有控制 | 仍可能停滞的原因 | 当前风险 |
| --- | --- | --- | --- |
| TASKS-WRITE | 当前卡上下文复制、严格 repository evidence | Agent 漏字段或仍复制错误 context；worker 长时间不完成 | 低到中 |
| TASKS-REVIEW | review gate、禁止 reviewer repository evidence、临时 adapter | 其他必填字段缺失；gate 身份、digest 或 artifact head 不一致 | 低到中 |
| IMPLEMENT | 精确 worktree/branch/MR、冻结基线、最多五轮修改、完成后 MR Ready | 实现耗时无 stage deadline；流水线或外部依赖长时间运行 | 中 |
| TEST | 当前 MR head、结构化 `skipped_unavailable`、不得修改代码 | 测试环境不可用、head 漂移、completion 上下文错误 | 中但可观测 |
| CODE-REVIEW | 与 tester 同 head、独立 GitLab 身份、汇总两方 findings | head 漂移会回到 TEST；失败最多进入五轮修复 | 中但受控 |
| MERGE | checked-head merge、pipeline、讨论、可合并性检查 | 条件不满足时无活动卡、只每 30 秒重试，缺少显式等待状态和通知 | 高 |

### 最终合并是现版本最明显的“看起来不动”路径

`hollysys_controller/gitlab.py:722-777` 要求：

- MR 已不是 Draft；
- tester 与 code-reviewer 都绑定当前 MR/head；
- 两个 gate 来自独立 GitLab 用户；
- MR 状态为 mergeable；
- 当前 head 的 required pipeline 必须为 `success`；
- 不存在未解决的 blocking discussion。

这些门禁本身是正确的。但 `hollysys_controller/service.py:1147-1158` 在
pipeline、discussion 或 MR readiness 不满足时，只返回并等待 30 秒后的 reconcile：

- 不创建活动卡；
- 不进入 exception；
- 不写出明确 `merge-wait` 状态；
- 不发送带 blocker 的通知；
- 没有等待总时限。

因此“TEST 和 CODE REVIEW 都完成、Controller health 正常、但没有活动卡也没有
合并”可能持续存在。这不是死锁，却会在用户侧表现为流程卡住，是长期改造的最高优先级
可观测性缺口。

### CODE 双门禁属于受控停止

`hollysys_controller/workflow.py:86-113` 的行为是：

1. TEST 完成后总是进入独立 CODE REVIEW，不因 test fail 提前跳过 review。
2. TEST 与 CODE REVIEW 不是同一 MR/head 时，重新从 TEST 开始。
3. 两者都 pass 且绑定同一 delivery 时才允许 merge。
4. 任一失败则回到 IMPLEMENT，最多五次 code modification。
5. 五次后仍未同时通过，形成明确 blocked/exception，由人类决定。

这一段可能停止自动流程，但属于有预算、有原因、有人工动作的受控停止，不应与无状态的
merge wait 或 worker hang 混为一类。

## 14. 长期改造新增要求

### Stage worker lease 与 watchdog

为每张正式工作卡持久化：

- `worker_started_at`
- `worker_session_id`
- `last_heartbeat_at`
- `last_progress_event_at`
- `deadline_at`
- `worker_pid/session_status` 的最近可信快照

Controller 必须区分：

1. 正常长任务：heartbeat 和 progress 持续；
2. worker 已退出：无进程/无 session，但卡仍 running；
3. worker 假活：有 heartbeat，但超过 stage progress deadline 无业务进展；
4. 外部依赖等待：有明确 dependency、deadline 和最近检查结果。

超时后先采集卡片、session、进程、最后事件和 worktree 证据，再进行有限重派；达到预算
后创建 exception。不得无限等待，也不得仅凭总运行时长杀死仍有真实进展的任务。

### 显式 merge-wait 状态

把当前 cardless retry 改为可持久化状态，例如：

```text
phase=code
stage=merge-wait
blocker=draft|pipeline_pending|pipeline_failed|not_mergeable|unresolved_discussion
mr_iid=<iid>
head_sha=<sha>
first_seen_at=<time>
last_checked_at=<time>
next_retry_at=<time>
```

要求：

- pipeline pending 时正常等待并显示 pipeline URL；
- pipeline failed/skipped 时立即形成可操作通知，不无限重试；
- Draft MR 超过短宽限期后通知 coder/管理员；
- unresolved discussion 列出 discussion URL 和责任人；
- blocker 变化产生事件，但相同 blocker 的轮询保持幂等；
- 超过可配置总时限后创建 merge exception，不消耗 Agent 协议预算；
- 合并前仍重新执行 checked-head 校验，不能因为等待状态而放宽门禁。

### Controller context envelope

长期移除 Agent 对以下字段的自由填写权：

- run、stage、iteration、mode；
- board、project、checkout、branch；
- card ID、parent ID；
- MR identity 中 Controller 已知且不可变的部分。

完成工具只接收业务 payload，Hermes/Controller 根据当前 scoped card 加盖 context。
若短期仍保留当前 schema，至少增加：

```text
hollysysctl validate-completion --card-id <id> --metadata <file>
```

它必须在 `kanban_complete` 前验证当前卡片上下文、schema、路径、MR/head 和字段权限，
避免“卡已经完成后才由 reconcile 发现错误”。

### 状态与通知验收

后续 E2E 必须分别制造并验证：

- worker 正常长任务；
- worker 退出但卡仍 running；
- completion 漏 `run_key`；
- 错 `checkout/iteration`；
- Hermes 注入 `worker_session_id`；
- reviewer 多带 `repository_evidence`；
- GitLab tree 查询超过 120 秒；
- MR 保持 Draft；
- pipeline pending、failed、skipped、success；
- unresolved discussion；
- TEST/CODE REVIEW head 漂移；
- 五次代码修复耗尽。

每一种情况都要断言：

- Controller daemon/socket 是否存活；
- `status-summary` 是否在 2 秒内返回；
- active card 或显式 wait/exception 是否唯一；
- event cursor 是否推进；
- outbox 通知是否幂等；
- 是否给出准确的人类动作；
- 重启后能否从持久化状态继续；
- 是否保持同一 run/worktree/branch/MR/head provenance。

## 15. 运维判定规则

### 不应立即重启

- `health=ok`；
- `event_lag=0` 或没有持续增加；
- active card 对应 worker 存在且有 heartbeat/progress；
- 只是完整 `status` 超时，而 `status-summary` 可快速返回；
- 正在执行已知 GitLab audit，且 endpoint/elapsed 仍变化。

### 必须进一步诊断

- active card 长时间不变且对应 worker/session 已消失；
- heartbeat 存在但超过 stage progress deadline 无业务事件；
- `event_lag` 持续增长；
- `last_reconcile_at` 超过
  `command_timeout + 2 * reconcile_interval` 不再前进；
- TEST/CODE REVIEW 完成后无 active card，且 merge blocker 未公开；
- socket 缺失、daemon 不存在或 `last_reconcile_error` 连续出现。

### 重启前必须保全

- `status-summary` 与 `health` 原始输出；
- Controller PID、worker PID/session、运行时长和命令；
- Controller 最近日志与当前 GitLab 子进程；
- Controller store 和对应 Kanban DB 的 SQLite online backup；
- 当前 run/card/iteration/worktree/branch/MR/head；
- pending outbox、failed operations 和 event cursor。

重启只恢复服务生命周期，不能解决非法 completion、错误 context、pipeline failure、
unresolved discussion 或 worker 业务逻辑停滞。恢复后必须核对 socket、cursor 和
唯一活动卡，不得重复创建 worktree、branch、MR 或下一阶段卡。

## 18. GitLab 故障处理的设计缺陷

### 固定次数把短暂故障升级为 fatal

当前配置：

```text
reconcile_interval_seconds=30
fatal_loop_error_limit=5
```

`hollysys_controller/daemon.py` 的 reconcile loop 对任意异常统一计数；连续五次后
直接重新抛出。GitLab connection refused、502、认证错误、协议错误和 Controller
内部不变量错误在这个边界上没有分类。

结果是约两分钟的 GitLab 故障足以终止 daemon。由于 Controller 是 Compose 容器主
进程，`restart: unless-stopped` 会重启整个容器，而不是只重启 Controller 服务。
启动时第一次 `reconcile_all()` 又在容器进入稳定服务前同步执行，只要 GitLab 仍为
502，就会形成快速 crash loop。

### 一个 Run 的外部错误会失败整个 reconcile

本次异常被包装为：

```text
RuntimeError:
hollysys-7ndsz4ixjjdkh6cjfkd4: command failed ...
```

它从单个 Run 的 GitLab MR 查询逃逸到 `reconcile_all()`，再逃逸到 daemon loop。
长期设计必须保证：

- 一个 Run 的外部依赖失败只把该 Run 标记为 dependency-degraded；
- 其他 Run、Kanban polling、RPC health、status-summary 和 outbox flush 继续运行；
- 外部错误不能与 Controller 自身数据库损坏、锁损坏或不变量破坏共用 fatal 预算。

### 健康状态缺少依赖退化语义

现有 health 主要展示当前探活结果和最近 reconcile error。故障恢复后
`last_reconcile_error=null`，但看不出：

- 最近一次 GitLab outage 的开始、结束和持续时间；
- 连续失败峰值；
- 容器因此发生的重启；
- 哪个 endpoint、Run、MR 或 head 受影响；
- 是否发送过故障与恢复通知。

这使历史告警到达后容易被误判为当前仍断连。

## 19. GitLab 长期改造要求

### 外部错误分类

至少分类为：

| 类型 | 示例 | 默认处理 |
| --- | --- | --- |
| `dependency_transient` | connection refused、timeout、TLS EOF、502/503/504 | 退避重试，保持 daemon 存活 |
| `dependency_rate_limited` | 429、Retry-After | 遵循服务端窗口，不累计 fatal |
| `dependency_auth` | 携带 Controller token 后的 401/403 | 明确配置异常并通知管理员 |
| `dependency_contract` | 确认 endpoint 正确后的 400/404/422 | run 级 exception 或代码缺陷 |
| `controller_fatal` | store 损坏、锁失效、不变量无法重建 | 停止 daemon，由 supervisor 恢复 |

未携带 token 的 curl 401 只能作为 TCP/TLS/HTTP 可达性证据，不能作为
`dependency_auth` 告警。

### Circuit breaker 与退避

GitLab client 按 host/endpoint 维护 circuit：

1. 首次瞬时失败立即记录 degraded 事件；
2. 使用指数退避和 jitter，例如 30、60、120、300 秒；
3. circuit open 期间不让每个 Run 重复轰炸同一 GitLab；
4. 使用轻量 `/api/v4/version` 或当前用户探活进入 half-open；
5. 成功后关闭 circuit，立即触发受影响 Run 的幂等 reconcile；
6. 发送一条恢复通知，引用 outage id、持续时间和受影响 Run；
7. 不因固定五次瞬时失败终止 daemon。

### 启动与服务生命周期

- Controller 启动时先打开 store、RPC socket、health 和本地
  `status-summary`，再异步执行首次 GitLab reconcile。
- 首次 GitLab 对账失败时 health 返回 `degraded`，而不是使进程退出。
- 若继续把 Controller 作为容器主进程，只有 `controller_fatal` 才允许整个容器退出。
- 更合理的方案是为 Controller、Gateway/Dashboard 和 profile workers 提供独立
  supervisor 生命周期；Controller 重启不应断开所有飞书连接。
- restart count、last exit reason 和 last successful reconcile 必须进入 health。

### Run 级隔离与持久化

- 在 Controller store 持久化
  `dependency_incident_id/first_seen/last_seen/failure_count/next_retry_at`；
- 记录受影响的 run/project/endpoint，但不得记录 token；
- Kanban event cursor、operation journal 和 outbox 不因 GitLab circuit open 而回退；
- 同一 outage 对同一 Run 只生成一个幂等通知；
- 恢复后从原 run/worktree/branch/MR/head 继续，不创建重复卡；
- 如果 outage 期间 MR head 漂移，恢复后重新校验 head，不复用旧 gate。

### 可观测性

health/status-summary 增加：

```text
dependencies.gitlab.state=ok|degraded|open|half_open
dependencies.gitlab.last_success_at
dependencies.gitlab.first_failure_at
dependencies.gitlab.last_failure_at
dependencies.gitlab.consecutive_failures
dependencies.gitlab.last_error_class
dependencies.gitlab.endpoint
dependencies.gitlab.next_retry_at
dependencies.gitlab.incident_id
container.restart_count
controller.last_exit_reason
```

通知必须成对：

- 故障通知：发生时间、错误类别、受影响 Run、下一次重试时间；
- 恢复通知：恢复时间、持续时长、重试次数、Run 是否自动续跑；
- 业务 triage/exception 必须使用不同消息类型，不能和 dependency outage 混淆。

## 20. GitLab 故障测试与验收

### 故障注入序列

集成测试至少重现本次真实序列：

```text
4 x TCP connection refused
1 x HTTP 502
3 x startup/reconcile HTTP 502
1 x success
```

并分别覆盖：

- DNS 解析失败；
- no route/timeout；
- TLS handshake/EOF；
- 429 + Retry-After；
- 携带 Controller token 后的 401/403；
- GitLab 500/502/503/504；
- 单个 project/MR 404；
- GitLab 恢复时 MR head 已漂移。

### 必须断言

1. transient/502 不终止 Controller daemon。
2. 容器 `RestartCount` 保持不变。
3. RPC socket、health、status-summary 和 Kanban polling 始终可用。
4. 一个 Run 失败不阻塞其他 Run 的本地状态和可继续操作。
5. 同一 outage 只发送一次故障通知和一次恢复通知。
6. 重试遵循退避，不按 Run 数量放大 GitLab 请求。
7. 恢复后 Controller 对原 MR/head 重新校验并幂等续跑。
8. token、请求 header 和敏感响应不进入日志或通知。
9. GitLab 仍故障时，业务 triage/exception 不被错误清除。
10. GitLab 已恢复但业务卡仍 triage 时，状态明确报告真实业务 blocker。

### 临时运维规则

在长期改造部署前：

1. 收到 GitLab 对账失败通知后先执行 host/container DNS、route、TCP/TLS 检查。
2. 使用 Controller token 重放通知中的精确只读 API，但不得打印 token。
3. 再检查 `health`、`status-summary`、socket、daemon PID、event cursor 和
   `RestartCount`。
4. 如果 GitLab 已恢复、health 为 ok、cursor 无 lag，不再重启容器。
5. 如果容器正在 crash loop，先保留日志和 SQLite online backup；GitLab 恢复后让
   Compose 自动启动，不反复手工 restart。
6. 把 connection refused、502、认证失败和业务 triage 分开报告。
7. 当前 Run 的 `note_2468` 必须按人类门禁处理，不能用网络恢复或容器重启代替。

## 23. 防止门禁时点倒置的长期改造

### 工件模型增加门禁阶段

所有 blocker、acceptance 和 evidence requirement 必须声明：

```text
gate_phase:
  implementation_entry
  implementation_completion
  migration_execution
  deployment_entry
  release_acceptance
```

不得只使用自然语言中的“实施前”“发布前”“完成前”。TASKS 编译时必须继承上游
gate phase，不能在没有明确 forced decision 的情况下把
`release_acceptance` 提升为 `implementation_entry`。

### DAG 验证增加语义规则

TASKS Review 除了无环和覆盖率，还必须检查：

- 根任务是否包含只能由目标环境或外部 owner 完成的验收；
- release gate 是否成为本地编码任务的前置依赖；
- 后续切片 blocker 是否被提升为全局根依赖；
- 每个外部 evidence task 是否有可在当前阶段完成的 owner 和输入；
- “准备脚本”“执行迁移”“部署验证”“发布验收”是否被拆成独立任务。

建议把 `OP-SRM-001` 拆分为：

```text
repository/local implementation preflight
target migration execution preflight
deployment/readback acceptance
```

只有第一个是编码入口；后两个分别阻塞迁移执行和完成声明。

### Human block 增加合同来源

`[human-block:v1]` 长期新增：

```text
contract_refs:
  - artifact
  - path
  - requirement_id
  - gate_phase
requested_decision_type
```

Controller 至少验证 requirement ID、工件 digest 和 gate phase 存在。Agent 新增
`implementation_entry_allowed` 一类令牌时，如果 schema 和冻结工件没有定义，应拒绝
该 required action，并让 Agent按上游合同自主继续或重新形成有来源的安全阻塞。

### Review 验收新增反例

测试必须包含：

1. PLAN 表示“未阻塞编码、阻塞完成声明”，TASKS 把证据放入唯一根任务时 review fail。
2. 目标环境不可用时，本地实现仍可继续，但迁移执行保持 blocked。
3. 后续 product blocker 不阻塞前置 SRM 切片。
4. skipped pipeline 不可作为 pass evidence，也不能单独否决本地编码入口。
5. human block required action 引用了未定义令牌时被拒绝。
6. 人类恢复只能调整门禁解释和授权，不能伪造环境 evidence 或 gate pass。

```text
依据冻结 PLAN 的 BLK-SRM-001，目标 PostgreSQL、DataSvc 部署和真实账号证据属于
发布/完成门禁，不阻塞本地实现。

允许 coder 继续仓库内代码、测试和迁移脚本开发。在目标数据库快照和部署证据被
owner 接受前，不得执行目标迁移、开放目标环境入口或声明最终交付完成。

BLK-PPR-001 只在进入对应产品规则消费任务前生效。无需新增

```

该答案的业务含义是调整错误的门禁时点，不是伪造环境证据，也不是放宽目标数据库、
部署或发布安全要求。

Dispatcher 必须从这条真实飞书事件取得：

- reply `message_id`
- sender open id
- chat id
- 原 thread id

随后调用：

```text
hollysysctl resolve
  run_key=hollysys-7ndsz4ixjjdkh6cjfkd4
  card_id=t_ab70c3b4
  block_id=hollysys-7ndsz4ixjjdkh6cjfkd4:t_ab70c3b4:27
  answer=<上述人类决策>
```

Controller 应验证 sender/chat/thread 与 Run origin 完全一致，再创建同一
`implement` stage 的新 attempt，把完整决策写入新卡 `resume_answer`。Dispatcher
不得直接调用 Kanban unblock/promote/complete。

### 为什么只在 GitLab 点击 resolved 不够

GitLab note `2468` 只是人类阻塞证据。Controller 的恢复授权还依赖：

- 原飞书 sender；
- 原 chat/thread；
- 新回复 message id；
- 精确 block id；
- 当前 card；
- 完整 answer。

只在 GitLab UI 解决 discussion 不会创建新的 IMPLEMENT attempt，也不会向 Coder
传递 `resume_answer`。反过来，只创建新卡而不收敛 GitLab discussion，又会在最终
checked-head merge 时被“unresolved blocking discussions”拦住。两个状态必须由同一
恢复操作一致收敛。

## 25. `triage` 无法通过当前 `resolve()` 恢复

### 真实状态

恢复前再次执行 `status-summary`：

```text
phase=code
stage=implement
card=t_ab70c3b4
status=triage
blocked=<note_2468 摘要>
event_cursor=409
kanban_max_event_id=409
event_lag=0
controller_health=ok
```

这证明卡片稳定停在合法 human block，而不是 Controller 未对账或 GitLab 再次离线。

### Controller 状态契约不一致

当前 `hollysys_controller/service.py` 有三种不同认识：

1. `ACTIVE_STATUSES` 包含 `triage` 和 `blocked`。
2. `status()` 与 `status_summary()` 对 `triage|blocked` 都展示 blocked 摘要。
3. `resolve()` 创建 retry 前却只接受：

```python
if task.status != "blocked":
    raise ValueError("card is not currently blocked")
```

旧卡收敛也只处理：

```python
if task.status == "blocked":
    complete old card as cancelled
```

Hermes 当前真实 `kanban_block` 结果是 `triage`，而 Controller 单元测试主要使用
人工构造的 `status="blocked"` fixture。于是：

- Controller 能展示该 human block；
- outbox 能通知人类；
- 人类也能给出正确答案；
- 但 `hollysysctl resolve` 仍可能以
  `card is not currently blocked` 拒绝恢复。

因此在部署兼容修复前直接回复飞书，业务决策是正确的，但技术恢复不可靠。

### 临时兼容修复要求

`resolve()` 应把带匹配合法 `[human-block:v1]` 的 `triage` 视为可恢复状态：

```text
resolvable statuses = blocked | triage
```

但不能只机械修改一个条件。完整要求：

1. 只有 matching block id、合法 kind、完整字段和正确 origin 才接受
   `triage`。
2. 幂等查找是否已经存在同 block/answer 的 retry。
3. 没有 retry 时创建同 stage 新卡，并写入 `resume_answer`、
   `resumed_from_card_id`。
4. 使用 Kanban 支持的正式状态转换把旧 `triage` 卡完成为
   `cancelled/superseded`；如果 Hermes 不允许直接 complete triage，先使用受支持的
   human-resolution transition，不能修改 SQLite。
5. 旧卡和新卡短暂并存时仍满足 Controller 已定义的 blocked-parent + retry 不变量。
6. 重放同一飞书 message id 返回同一恢复结果，不重复创建卡。
7. 新卡成功发布后再生成 resumed outbox，避免通知先于状态落盘。
8. 恢复操作应找到 note `2468` 所属 discussion，并在确认 human resolution 已持久化
   后标记 resolved；失败时记录可重试 operation，不丢失新卡。

### 必须新增的测试

- Hermes `kanban_block` 返回 `triage` 后可以 resolve。
- 传统 `blocked` 状态仍可 resolve。
- 普通 triage、没有 `[human-block:v1]` 的 triage 必须拒绝。
- 错 block id、错误 sender/chat/thread 必须拒绝。
- 同一 reply 重放不创建第二张 IMPLEMENT 卡。
- 旧 triage 卡被可审计地标记 cancelled/superseded。
- 新卡保留相同 run/worktree/branch/MR，并携带完整 `resume_answer`。
- GitLab discussion 在状态落盘后 resolved；GitLab 暂时失败时进入幂等重试。
- 最终 merge 不再因已经人类解决的 note `2468` 保持 unresolved。

### 恢复后的验收

完成兼容修复并由原发起人答复后，必须看到：

```text

old_outcome=cancelled
old_resolution=<human-resolution:v1>
new_card=<different t_xxx>
new_stage=implement
new_status=todo|ready|running
new_resume_answer=<完整人类决策>
blocked=null
event_lag=0
```

同时核对：

- MR/head/TASKS digest 未漂移；
- worktree、branch 和 MR 没有重复创建；
- note `2468` discussion 已 resolved；
- Coder 开始本地实现，但没有执行目标迁移或伪造部署证据；
- `BLK-PPR-001` 仍在正确的后续任务入口生效。

### 禁止的临时做法

- 直接编辑 Kanban SQLite；
- 手工把 triage 改成 done；
- Dispatcher 调用 Kanban unblock/promote；
- 重启容器以期解除业务阻塞；
- 只解决 GitLab note 而不执行 Controller resolve；
- 伪造 PostgreSQL/DataSvc 证据；
- 补写没有合同来源的 `implementation_entry_allowed=true`。

## 26. GitLab 全仓递归查询的触发链、阻塞机理与改造要求

### 结论

本次出现的“全仓 GitLab 递归查询”不是 Coder 在搜索业务代码，也不是 Controller
在下载整个仓库的所有文件内容。它是 Controller 为验证冻结文档集合没有被新增、删除
或重命名，先递归枚举指定 commit 下的全部仓库路径，再从中筛选符合 artifact glob
的文件并计算基线摘要。

对应请求为：

```text
glab api projects/21/repository/tree \
  ?ref=<immutable-head-sha>&recursive=true&per_page=100 \
  --hostname green-git.hollysys.net \
  --paginate \
  --output ndjson
```

`recursive=true` 返回的是仓库树中的路径/blob 元数据；只有筛选后命中
`docs/prds/*/specs/spec-*.md` 等规则的文件才继续读取内容。问题不在于需要验证
artifact 集合，而在于同一个不可变 SHA 被重复全仓分页扫描，且扫描发生在 Controller
全局锁内。

### 精确调用链

配置中的 SPEC、PLAN、TASKS artifact 使用 glob，而不是单个固定路径。为了证明
“文件集合没有变化”，仅重新读取旧文件是不够的，还必须发现：

- 新增的匹配文件；
- 删除的匹配文件；
- 重命名后进入或离开匹配范围的文件；
- 同一 artifact 类型下文件数量的变化。

因此当前实现执行以下链路：

```text
status()
  -> validate document gate artifacts
     -> GitLabClient.artifact_paths()
        -> repository/tree?recursive=true
  -> validate frozen baselines
     -> GitLabClient.validate_baseline_at_ref()
        -> artifact_paths()
           -> repository/tree?recursive=true
```

一次完整 `status()` 会分别处理 SPEC、PLAN、TASKS，并在门禁检查和冻结基线检查中
再次读取。因此同一个 MR head 最坏会触发约 6 次全仓递归树查询。

恢复阻塞卡时还有另一条链路：

```text
resolve()
  -> _create_work()
     -> _frozen_violation()
        -> validate_baseline_at_ref()
           -> artifact_paths()
              -> repository/tree?recursive=true
```

PRD 是直接路径读取，SPEC、PLAN、TASKS 是 glob，恢复时最多又产生 3 次递归树查询。
当前没有按 `(project_id, immutable_commit_sha, pattern_set)` 复用结果，所以相同 SHA
会被反复扫描。

### 本次现场证据

现场曾观察到 Controller PID `208` 的子进程：

```text
glab api projects/21/repository/tree?ref=b1eefe0b...&recursive=true&per_page=100 \
  --hostname green-git.hollysys.net --paginate --output ndjson
```

同时：

- Dispatcher 的完整 `hollysysctl status` 在约 `130.47s` 后超时；
- Controller 配置的 command timeout 为 `120s`；
- Controller 进程、Unix socket、Kanban 和基础 GitLab health 均正常；
- MR、note、current-user 等小请求能快速返回；
- 慢的是 repository tree 的递归分页链路，而不是 GitLab 整体不可访问；
- 客户端 RPC 超时后，服务端原请求及其 `glab` 子进程仍可能继续执行；
- 随后发起的 `resolve()` 会排在旧查询后面，表现为“健康正常，但 status/resolve
  一直不返回”。

因此此前的 `connect: connection refused` 是一次真实的 GitLab 连通性故障；本次
`status`/`resolve` 卡顿则是另一类问题：昂贵的递归树查询、重复工作、锁粒度和超时
取消机制共同造成。两者不能混为一谈。

### 为什么会拖住整个 Run

当前 `status()` 和 `resolve()` 都在持有 Controller 的全局 `self._lock` 时执行
GitLab 网络访问。只要一次全仓分页扫描变慢：

1. 当前请求长期占有全局锁；
2. 同一 Run 的查询和恢复请求排队；
3. 其他需要该锁的操作也会等待；
4. 客户端在约 130 秒放弃，但服务端工作不一定取消；
5. Dispatcher 再次查询会叠加新请求，使现场看起来像 Controller “卡死”。

`health` 只证明进程和基础依赖仍可响应，不能证明某个持锁的 Run 对账已经完成。
这解释了“health=ok、socket 存在，但 status 连续超时”的表象。

### 当前临时运维规则

在长期改造完成前：

1. 高频查看进度使用：

   ```text
   hollysysctl status-summary --run-key <run-key>
   ```

2. 完整 `status` 只作为显式 GitLab 审计使用，不要在每次 `resolve` 前重复执行。
3. 完整 `status` 超时后，先检查 Controller 是否仍有
   `repository/tree?recursive=true` 的 `glab` 子进程；不要立即判断 Controller
   离线。
4. 不要连续叠加多个完整 `status` 请求，也不要让 Dispatcher 轮询完整审计。
5. 恢复命令已经提交后，先观察事件游标、卡片状态和子进程，再决定是否重试。
6. 活跃 Coder 正在执行时，不因只读查询超时就重启容器或杀死工作进程。

### 长期改造要求

1. **不可变 SHA 缓存**
   按 `(project_id, commit_sha, artifact-pattern fingerprint)` 缓存仓库路径集合和
   artifact digest。Git commit SHA 不可变，同一个 key 不需要重复访问 GitLab。

2. **单次请求内复用**
   一次 `status()` 先计算 artifact snapshot，门禁检查和冻结基线检查共享同一份
   结果，禁止同一 stage 重复扫描。

3. **恢复路径复用已验证基线**
   当 MR 当前 head 与已记录的 validated head 完全相同，且 pattern 和 frozen
   baseline 均未变化时，同阶段 human resume 可以复用此前审计结果。head 变化时
   必须回退到实时验证，不能跳过防漂移检查。

4. **分离本地状态与远端审计**
   将快速、权威的 Controller/Kanban 状态查询与昂贵的 GitLab live audit 分开。
   `status-summary` 应保持本地快速路径；完整审计应由显式选项（例如
   `status --audit`）触发。

5. **缩小锁范围**
   GitLab 只读网络 I/O 不应发生在全局锁内。先在锁内快照 run、head 和基线，
   释放锁后读取 GitLab，再重新加锁并通过版本/head 比较或 CAS 确认快照仍有效，
   最后落盘。

6. **超时传播与取消**
   RPC 客户端超时必须取消服务端请求及其 `glab` 子进程，不能让已无人等待的查询
   继续持锁运行。

7. **Singleflight 合并**
   并发请求相同 `(project, sha, patterns)` 时只允许一个 GitLab tree scan，其余
   请求等待并共享结果。

8. **可选的本地 Git 快速路径**
   可以在确认本地 object、remote、MR head 和 worktree provenance 完全一致后，
   使用精确 SHA 的 `git ls-tree` 枚举路径；GitLab MR head 仍是权威来源。不满足
   provenance 条件时必须使用 GitLab。

9. **补充可观测性**
   每次扫描记录 scan key、页数、路径数、命中数、耗时、cache hit/miss、
   singleflight wait、deadline 和 cancel reason，便于区分连通故障与性能阻塞。

### 必须新增的测试和验收

- 相同 SHA 连续执行完整状态检查，只发生一次远端树扫描，后续命中缓存。
- 一次 `status()` 的 gate 与 frozen baseline 不重复扫描同一 artifact 集合。
- 相同 head 的 human resume 可复用验证结果；head 改变时强制实时审计。
- RPC 超时后服务端任务和 `glab` 子进程均被取消，不继续占锁。
- GitLab tree 响应慢时，`health`、`status-summary` 和无关 Run 仍可及时返回。
- 新增、删除、重命名匹配 artifact 时，冻结基线必须可靠报错。
- 缓存绝不能跨 project、SHA 或 pattern fingerprint 复用。
- 完整审计超时返回明确的 degraded/audit-timeout，不把 Controller 报成离线。
- 并发相同扫描只发起一次 GitLab 请求。
- 日志能够给出每次扫描耗时和缓存命中证据。
